# Avito Backend Trainee Assignment Autumn 2026
## CJM для клиента
### Поиск заведения
Пользователь открывает список заведений. 


Связь с сервером через `GET /restaurants`

### Просмотр меню заведения (список блюд)
Пользователь получает список блюд с названием, наличием и ценой


Связь с сервером через `GET /restaurants/{id}/menu`, где `id` - ID заведения

### Просмотр информации о блюде (получение блюда)
Пользователь получает название блюда, описание, состав, наличие и цену.


Связь с сервером через `GET /restaurants/{id}/dishes/{dish_id}`

Пользователь может столкнуться с проблемой, когда получает информацию о блюде, но блюдо было удалено.
В таком случае вернуть пользователю 404 Not Found.

### Добавление блюда в заказ
Пользователь добавляет блюдо в заказ. К блюду можно добавить модификаторы в виде дополнительных ингридиентов.


Связь с сервером через `POST /cart/items`, передавая ID блюда, список модификаторов и ID заведения.


Возможна проблема, когда пользователь попытается добавить блюда из разных ресторанов. 
Будем возвращать 409 Conflict в случае, если новое блюдо в корзине не принадлежит заведению остальных

### Просмотр корзины (получение списка блюд из корзины)
Пользователь просматривает блюда в своей корзине.


Связь с сервером через `GET /cart/items`


Может возникнуть проблема, когда заведение удалило блюдо из корзины, но пользователь уже его добавил.
В таком случае нужно проверять у каждого блюда его актуальное наличие в заведении.


### Изменение корзины (удаление блюда)
Пользователь удаляет блюдо из корзины.


Связь с сервером через `DELETE /cart/items/{item_id}`


### Изменение корзины (изменение количества блюда)
Пользователь меняет количество блюда в корзине.


Связь с сервером через `PATCH /cart/items/{item_id}`, предавая новое количество.

Может возникнуть ситуация, когда пользователь установил количество на <= 0. 
В таком случае вызываем удаление блюда из корзины.

### Оформление заказа
Пользователь оформляет заказ: вводит адрес, выбирает способ оплаты и отправляет заказ заведению.


Связь с сервером через `POST /orders`

Может возникнуть проблема, когда пользователь указал адрес доставки, находящийся далеко от заведения.
Для решения этой проблемы необходимо проверять зону, введенная пользователем и зоны заведения.


### Отмена заказа
Пользователь отменяет заказ после оформления


Связь с сервером через `POST /orders/{id}/cancel`

Проблема может возникнуть при попытке отменить заказ, который уже был доставлен. 
Для этого перед отменой проверяем, находится ли заказ в одном из статусов: new, accepted, in_process


### Просмотр статуса заказа
Пользователь просматривает статус заказа после оформления


Связь с сервером через `GET /orders/{id}/status`

## CJM для заведения
### Просмотр меню
Заведение просматривает список всех блюд. Заведение видит ID, название, цену и наличие.
Связь через `GET /admin/restaurants/{id}/menu`.


### Управление меню (добавление блюда)
Заведение добавляет новые блюда в свой каталог. Для блюда указывается название, описание, состав и цена. 
Наличие по умолчанию устанавливается на true.


Связь с сервером через `POST /admin/restaurants/{id}/dishes`. 


Может возникнуть проблема, когда заведение пытается добавить блюдо с пустым названием, отрицательной или пустой ценой.
Решить можно валидацией на стороне сервера и возвратом 400 Bad Request.

### Управление меню (изменение блюда)
Заведение изменяет блюдо: название, описание, состав, наличие и/или цену.

Связь с сервером через `PATCH /admin/restaurants/{id}/dishes/{dish_id}`.


Может возникнуть проблема, когда заведение изменяет блюдо, которое уже заказал пользователь.

В таком случае, когда блюдо уже заказано, а заведение меняет название или цену. 
При оформлении заказа сервер копирует в order_items снимок: dish_name, dish_price, количество, снимок модификаторов (название + цена), итог позиции. 
Состав заказа читается только из снимка и не меняется при правках блюда.

Еще может возникнуть проблема, когда наличие выставлено в false, а блюдо уже заказано. 
Оформленный заказ не меняется, заведение готовит по снимку либо отклоняет заказ с причиной. 
В активных корзинах позиция помечается недоступной, оформление с ней блокируется с ошибкой 409.


Еще может возникнуть проблема, когда заведение изменило наличие блюда на "нет в наличии", но блюдо уже заказано.
В таком случае блюдо не пропадает у пользователя из уже оформленного заказа.


### Управление меню (удаление блюда)
заведение удаляет блюдо из своего меню.

Связь с сервером через `DELETE /admin/restaurants/{id}/dishes/{dish_id}`.

Блюдо и его модификаторы удаляются физически, повторный вызов возвращает 404. 
Восстановление невозможно, пересоздание даёт новый ID.

Может возникнуть проблема, когда блюдо уже заказано. 
Удаление не блокируется и не влияет на заказы. Состав читается из снимка order_items, ссылка dish_id обнуляется.

### Управление модификаторами блюд
Заведение создаёт доп. ингредиенты, задаёт цену и наличие, привязывает к блюдам. 

Связь с сервером через `GET|POST /admin/restaurants/{id}/modifiers`, `PATCH|DELETE /admin/restaurants/{id}/modifiers/{modifier_id}`.


Возможна проблема, когда модификатор удалён или снят с наличия, а он в корзине или в заказе. 
В заказе остаётся снимок и история не меняется. 
Позиция корзины с недоступным модификатором помечается недоступной и возвращает ошибку 409 при оформлении.


### Зоны доставки
Заведение задаёт зоны, по которым при оформлении проверяется адрес клиента.


Связь с сервером через `GET|PUT /admin/restaurants/{id}/delivery-zones`


Проблема возможна, когда zones не заданы. Пока список пуст, заказы не принимаются и клиент получает отказ при оформлении.


### Обработка заказа
Заведение получает новые заказы polling'ом `GET /admin/restaurants/{id}/orders?status=new` каждые 15–30 с. Состав, адрес, способ оплаты и сумма: `GET /admin/restaurants/{id}/orders/{order_id}`.
Принятие - `POST .../accept` (accepted), отклонение с причиной - `POST .../reject` (rejected). 
Оба действия допустимы только из new и выполняются атомарно; если клиент отменил заказ или другой сотрудник уже обработал его -> 409 Conflict с актуальным статусом.
Проблема: заведение игнорирует заказ. Фоновый планировщик отменяет заказы в статусе new старше 10 минут от created_at -> cancelled, причина timeout.

### Обновление статуса заказа
Разрешены только переходы accepted -> in_process -> ready через `PATCH .../status`.
Проблема: клиент отменил заказ (доступно в new, accepted, in_process), а заведение считает его активным. 
Отменённые и отклонённые заказы уходят из выборки активных. Если заказ был в готовке, то приготовление останавливается.

## Стек
- Язык программирования: C#, .NET9.0
- Фреймворк Web API: ASP.NET
- Архитектура: Clean Architecture, паттерн CQRS с использованием MediatR
- База данных: PostgreSQL
- ORM: EntityFramework Core
- Инфраструктура: Docker, Docker Compose
- Тестирование: xUnit + Moq
- Документация API: [Scalar](https://scalar.com/docs-for/dotnet)
