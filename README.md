# Avito Backend Trainee Assignment Autumn 2026
# CJM для клиента (MVP)

**Общее:** клиент аутентифицирован (иначе 401); корзина и заказы доступны только владельцу, чужие/несуществующие объекты -> 404. Ошибки валидации -> 400, конфликты состояния -> 409. В MVP оплата при получении, онлайн-оплата и возвраты вне скоупа.

### Поиск заведения
Пользователь открывает список заведений и получает ID и название.
`GET /restaurants` -> 200 OK.

### Просмотр меню заведения
Пользователь получает список блюд: ID, название, наличие, цена, а также доступные модификаторы блюда (ID, название, цена).
`GET /restaurants/{id}/menu`, где `id` - ID заведения -> 200 OK.

### Просмотр информации о блюде
Пользователь получает название, описание, состав, наличие, цену и доступные модификаторы.
`GET /restaurants/{id}/dishes/{dish_id}` -> 200 OK.

*Проблема: блюдо удалено заведением.* Возвращаем 404 Not Found.

### Добавление блюда в корзину
Пользователь добавляет блюдо с модификаторами (доп. ингредиенты) и количеством.
`POST /cart/items` с ID заведения, ID блюда, списком ID модификаторов и количеством -> 200 OK (новое количество позиций в корзине).
Позиция пишется в `cart_items` со снимком названия и цены блюда и модификаторов на момент добавления.

*Проблема: блюда из разных заведений.* Если корзина не пуста и ID заведения не совпадает -> 409 Conflict.
*Проблема: блюдо или модификатор удалены/сняты с наличия* -> 404 для блюда, 400 для недоступного модификатора.

### Просмотр корзины
Пользователь видит позиции: ID, название и цена на момент добавления, модификаторы, количество, признак доступности и актуальная цена, если она изменилась.
`GET /cart/items` -> 200 OK.

*Проблема: заведение удалило блюдо из меню или сняло его с наличия, а оно лежит в корзине.* Для каждой позиции проверяется: блюдо удалено (`dish_id = NULL`) ИЛИ `is_available = false` ИЛИ модификатор недоступен. Такая позиция помечается недоступной и остаётся в корзине до удаления пользователем.

### Изменение корзины (удаление позиции)
`DELETE /cart/items/{item_id}` -> 204 No Content; чужая или несуществующая позиция -> 404.

### Изменение корзины (изменение количества)
`PATCH /cart/items/{item_id}` с новым количеством -> 200 OK.

*Проблема: количество ≤ 0.* Позиция удаляется из корзины, ответ 204 No Content.

### Оформление заказа
Пользователь вводит адрес, выбирает способ оплаты и отправляет заказ заведению.
`POST /orders` -> 201 Created (ID заказа, статус `new`). Сервер копирует позиции корзины в `order_items` снимком (название, цена, количество, модификаторы с ценами, итог позиции) и очищает корзину. Состав заказа дальше читается только из снимка.

*Проблема: адрес вне зоны доставки заведения.* Введённый адрес проверяется на попадание в зоны заведения -> 422 Unprocessable Entity. Если зоны не заданы - заказ не принимается, тот же отказ.
*Проблема: пока пользователь собирал корзину, блюдо или модификатор стали недоступны либо изменилась цена.* Перед созданием заказа позиции перепроверяются -> 409 Conflict со списком проблемных позиций, заказ не создаётся.

### Просмотр заказа
Пользователь смотрит состав оформленного заказа: позиции из снимка, адрес, способ оплаты, итоговую сумму, статус.
`GET /orders/{id}` -> 200 OK. Правки и удаления блюд заведением на состав не влияют.

### Просмотр статуса заказа
`GET /orders/{id}/status` -> 200 OK. Клиент опрашивает статус каждые 10–15 с и так узнаёт о принятии, отклонении (`rejected`) и авто-отмене по таймауту (`cancelled`, причина `timeout`, 10 минут без реакции заведения).

### Отмена заказа
`POST /orders/{id}/cancel` -> 200 OK (`cancelled`).

*Проблема: заказ уже доставлен, отклонён или отменён.* Отмена допускается только в статусах `new`, `accepted`, `in_process`, переход выполняется атомарно; иначе -> 409 Conflict с актуальным статусом.

# CJM для заведения (MVP)

**Общее:** все ручки под `/admin/restaurants/{id}/...`; сервер проверяет аутентификацию (401) и принадлежность `{id}` текущему заведению (403), чужие/несуществующие объекты -> 404. Валидация на сервере -> 400 Bad Request, конфликты состояния -> 409 Conflict.
Архивных блюд нет: удаление физическое, восстановление невозможно. История заказов и корзин хранится снимком и не зависит от таблицы блюд: ссылки `dish_id` и `modifier_id` обнуляются при удалении (`ON DELETE SET NULL`).

**Статусы заказа:** `new -> accepted -> in_process -> ready -> delivered`; терминальные - `rejected` (отклонено заведением) и `cancelled` (отменено клиентом или по таймауту). Переходы только по цепочке и атомарно. `ready -> delivered` - зона доставки/выдачи, вне этого CJM.

### Просмотр меню
Заведение видит список своих блюд: ID, название, цена, наличие.
`GET /admin/restaurants/{id}/menu` -> 200 OK.

### Управление меню (добавление блюда)
Указываются название, описание, состав и цена; наличие по умолчанию `true`.
`POST /admin/restaurants/{id}/dishes` -> 201 Created (ID блюда).

*Проблема: пустое название, отрицательная или пустая цена.* Валидация на сервере: название непустое после trim и с лимитом длины, цена - decimal > 0, описание и состав опциональны -> 400 Bad Request.

### Управление меню (изменение блюда)
Заведение меняет название, описание, состав, наличие и/или цену.
`PATCH /admin/restaurants/{id}/dishes/{dish_id}` -> 200 OK; правила валидации те же, что при создании (400), блюдо не найдено -> 404.

*Проблема: блюдо уже заказано, а заведение меняет название или цену.* При оформлении заказа сервер копирует в `order_items` снимок: `dish_name`, `dish_price`, количество, снимок модификаторов (название + цена), итог позиции. Состав заказа читается только из снимка и не меняется при правках блюда.

*Проблема: наличие выставлено в `false`, а блюдо уже заказано или лежит в корзинах.* Оформленный заказ не меняется: заведение готовит по снимку либо отклоняет заказ с причиной, пока он в статусе `new`. В активных корзинах позиция помечается недоступной, оформление с ней блокируется с 409.

### Управление меню (удаление блюда)
Заведение удаляет блюдо из своего меню.
`DELETE /admin/restaurants/{id}/dishes/{dish_id}` -> 204 No Content; повторный вызов или чужое блюдо -> 404.
Блюдо удаляется физически вместе с привязками к модификаторам; сами модификаторы общие для заведения и остаются. Пересоздание даёт новый ID. Основной способ временно убрать блюдо - наличие `false`, а не удаление.

*Проблема: блюдо уже заказано.* Удаление не блокируется и не влияет на заказы: состав читается из снимка `order_items`, ссылка `dish_id` обнуляется.
*Проблема: блюдо лежит в корзинах пользователей.* Позиции остаются с названием и ценой на момент добавления, `dish_id = NULL`, помечаются недоступной; оформление с ними -> 409.
*Проблема: клиент открыл карточку удалённого блюда* -> 404 Not Found.

### Управление модификаторами блюд
Заведение создаёт доп. ингредиенты, задаёт цену и наличие, привязывает к блюдам.
`GET|POST /admin/restaurants/{id}/modifiers`, `PATCH|DELETE /admin/restaurants/{id}/modifiers/{modifier_id}` -> 200/201/204; валидация названия и цены как у блюд (400), удаление физическое.

*Проблема: модификатор удалён или снят с наличия, а он в корзине или заказе.* В заказе остаётся снимок (название + цена), история не меняется. Позиция корзины с недоступным модификатором помечается недоступной, сервер возвращает 409 при оформлении.

### Зоны доставки
Заведение задаёт зоны, по которым при оформлении проверяется адрес клиента.
`GET|PUT /admin/restaurants/{id}/delivery-zones` -> 200 OK; некорректные зоны -> 400.

*Проблема: зоны не заданы.* Пока список пуст, заказы не принимаются: клиент получает 422 при оформлении.

### Обработка заказа
Заведение получает новые заказы polling'ом `GET /admin/restaurants/{id}/orders?status=new` каждые 15–30 с (пагинация, сортировка по времени создания). Состав, адрес, способ оплаты и сумма: `GET /admin/restaurants/{id}/orders/{order_id}` -> 200 OK.
Принятие - `POST /admin/restaurants/{id}/orders/{order_id}/accept` (`accepted`), отклонение с причиной - `POST /admin/restaurants/{id}/orders/{order_id}/reject` (`rejected`).

*Проблема: гонка - клиент отменил заказ или второй сотрудник уже обработал его.* Оба действия допустимы только из `new` и выполняются атомарно (условный UPDATE по текущему статусу); иначе -> 409 Conflict с актуальным статусом.

*Проблема: заведение игнорирует заказ.* Фоновый планировщик отменяет заказы в статусе `new` старше 10 минут от `created_at` -> `cancelled`, причина `timeout`. Клиент видит это при опросе статуса.

### Обновление статуса заказа
Разрешены только переходы `accepted -> in_process -> ready`.
`PATCH /admin/restaurants/{id}/orders/{order_id}/status` -> 200 OK. Переход атомарный, по текущему статусу в БД; неизвестный статус -> 400.

*Проблема: клиент отменил заказ (доступно в `new`, `accepted`, `in_process`), а заведение считает его активным.* Отменённые и отклонённые заказы уходят из выборки активных; переход из терминального статуса или недопустимый переход (`new -> ready`, назад) -> 409 Conflict с актуальным статусом. Если заказ был в готовке - приготовление останавливается.

## Стек
- Язык программирования: C#, .NET9.0
- Фреймворк Web API: ASP.NET
- Архитектура: Clean Architecture, паттерн CQRS с использованием MediatR
- База данных: PostgreSQL
- ORM: EntityFramework Core
- Инфраструктура: Docker, Docker Compose
- Тестирование: xUnit + Moq
- Документация API: [Scalar](https://scalar.com/docs-for/dotnet)
